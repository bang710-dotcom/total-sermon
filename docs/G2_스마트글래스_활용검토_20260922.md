# 이븐 리얼리티 G2 스마트 글래스 — 목회·설교 활용 가능성 검토

작성 2026-09-22 · 대상: 토탈 설교 앱(v576) 연계 및 목회 환경 신규 앱

---

## 0. 결론 요약

**가능합니다. 그것도 예상보다 훨씬 유리한 조건입니다.**

세 가지가 동시에 맞아떨어집니다.

1. **G2 앱은 "웹앱"입니다.** 네이티브 앱이 아닙니다. 내 서버에 올린 웹페이지를 아이폰 Even 앱이 WebView로 열고, 화면과 입력만 BLE로 안경에 중계합니다. 즉 **설교앱과 똑같은 기술 스택(HTML/JS + 구글시트 백엔드)을 그대로 씁니다.**
2. **한글이 펌웨어 폰트에 들어 있습니다.** 공식 폰트 측정 라이브러리로 직접 검증했습니다(§2-2).
3. **카드원고가 이미 "한 화면 단위"로 만들어져 있습니다.** 실측 결과 가장 긴 예화 카드도 G2 한 화면 10줄 중 4줄만 씁니다(§2-3). 설교앱이 이미 만들어 두는 `파일맵.cardArr` 가 **그대로 G2 페이지 배열이 됩니다.** 새로 쓸 콘텐츠가 사실상 없습니다.

가장 먼저 만들 것은 **강단 프롬프터(카드원고 HUD)** 입니다. 반나절이면 동작하는 시제품이 나옵니다.

## 1. 플랫폼 구조 — 왜 설교앱에 유리한가

### 1-1. 실행 구조

```
[내 서버 / Cloudflare Pages]  ──HTTPS──▶  [아이폰 Even 앱 WebView]  ──BLE──▶  [G2 안경]
       (내 코드가 여기서 돎)                    (중계만 함)                  (화면 + 입력)
```

- 안경에서는 **코드가 돌지 않습니다.** 안경은 "컨테이너를 그리는 디스플레이 + 탭/스크롤을 보내는 입력장치"입니다.
- 내 웹앱은 평범한 웹앱입니다 — 자체 백엔드, DB, API 키를 그대로 씁니다.
- SDK가 WebView에 `EvenAppBridge` 라는 JS 다리를 주입하고, 내 JS가 그걸 호출해 화면을 그립니다.

**설교앱에 주는 의미**: 구글시트 Apps Script 웹앱(`Code.gs`)을 **그대로 백엔드로 재사용**할 수 있습니다. 설교 데이터·카드원고·전환표가 이미 거기 있습니다. G2용으로 새 서버를 세울 필요가 없습니다.

> 주의: `app.json` 의 `network` 권한 화이트리스트에 `https://script.google.com` 을 넣어야 하고, 화이트리스트는 **CORS 우회가 아닙니다.** WebView는 진짜 브라우저 엔진이라 CORS가 그대로 걸립니다. 지금 설교앱이 브라우저에서 시트를 호출하고 있으므로 이미 통과하는 구성이지만, 실제 연결 때 첫 번째로 확인할 항목입니다.

### 1-2. 하드웨어

| 항목 | 사양 |
|---|---|
| 디스플레이 | 마이크로 LED 양안, **576 × 288 px / 눈**, 4비트 그레이스케일(초록 16단계) |
| 입력 | 안경다리 터치(탭/더블탭), **R1 반지**(스크롤·탭·더블탭) |
| 마이크 | 있음 — 16kHz PCM S16LE 모노, SDK로 접근 가능 |
| 카메라 | **없음** |
| 스피커 | **없음** |
| 기타 | 착용 감지, 배터리 상태, BLE 5.x(실사용 약 28m) |

카메라·스피커가 없다는 점은 **강단·심방 환경에서는 오히려 장점**입니다. 회중이나 성도가 "촬영당한다"고 느낄 여지가 없습니다.

### 1-3. 화면 모델 (중요한 제약)

- **CSS·flexbox·DOM이 없습니다.** 절대좌표 픽셀 컨테이너만 있습니다.
- 페이지당 컨테이너 **최대 12개**(텍스트/리스트 8 + 이미지 4).
- 폰트는 펌웨어에 구워진 **LVGL 단일 폰트 1종**. 크기·굵기·기울임 선택 불가, **가운데 정렬도 없습니다**(공백으로 수동 패딩).
- 배경색·채우기 없음. 흰 픽셀 = 밝은 초록, 검정 픽셀 = 꺼짐(투명).
- **폰트에 없는 글자는 조용히 사라집니다**(대체 글리프도 안 뜸).
- 강조는 **테두리(`borderWidth`) 토글**과 `>` 같은 커서 문자로만 합니다.

→ 설교앱의 빨간 볼드(성경 인용)·파란 볼드(예화) 같은 **색 강조는 G2에서 재현 불가**입니다. 대신 들여쓰기·구분선(`─ ━`)·머리 기호로 구분해야 합니다.

### 1-4. 성능 실측치 (커뮤니티 계측, 펌웨어 2.2.7.14 / SDK 0.0.13)

| 호출 | 비용 |
|---|---|
| `rebuildPageContainer`(화면 통째 교체) | **~165 ms**, 컨테이너 수와 무관하게 일정 |
| `textContainerUpgrade`(텍스트 한 칸만) | ~83 ms / 호출 |
| `updateImageRawData`(이미지) | ~104 ms 고정 + KB당 ~3.9 ms |

핵심은 **"호출당 고정비가 지배한다"** 입니다. 데이터 크기는 거의 무관합니다.

- **카드 넘김 = 화면 통째 교체 = 약 165 ms** → 체감상 즉시입니다. 프롬프터로 전혀 문제없습니다.
- 텍스트 칸을 3개 이상 따로 고치면 통째 교체보다 **느립니다**(손익분기 2개). 카드 전체를 다시 그리는 편이 낫습니다.
- 이미지 애니메이션은 최대 ~9.5 fps — 설교 용도에는 애초에 필요 없습니다.

## 2. 검증한 것 (실측)

### 2-1. 한국어는 공식 지원 언어입니다

`app.json` 의 `supported_languages` 가 허용하는 값은 `en, de, fr, es, it, zh, ja, **ko**` 입니다. 한국어가 플랫폼 차원에서 정식 항목으로 들어가 있습니다.

### 2-2. 한글 글리프 존재 검증 — 직접 측정

공식 폰트 측정 라이브러리 `@evenrealities/pretext`(펌웨어 LVGL 렌더링을 픽셀 단위로 재현)를 설치해 코드포인트별 자폭(advance width)을 조회했습니다. **자폭 0 = 폰트에 글자가 없음** 입니다.

| 글자 | 코드포인트 | 자폭 | 판정 |
|---|---|---|---|
| 가 | U+AC00 | 18.38 px | ✅ 있음 |
| 힣 | U+D7A3 | 18.38 px | ✅ 있음 |
| 하 · 나 · 님 · 뜻 | — | 모두 18.38 px | ✅ 있음 |
| ㄱ (자모) | U+3131 | 18.38 px | ✅ 있음 |
| 日 (한자) | U+65E5 | 20.00 px | ✅ 있음 |
| あ (가나) | U+3042 | 20.00 px | ✅ 있음 |
| 「 · ～ · “ · … · · | — | 있음 | ✅ 문장부호 정상 |
| **ก (태국어)** | U+0E01 | **0.00 px** | ❌ **없음 (대조군)** |

태국어가 0으로 나온다는 것이 이 측정이 유효하다는 증거입니다(실제로 커뮤니티에 "G2 펌웨어에 태국어 비트맵 폰트를 이식하는" 프로젝트가 따로 있습니다). **한글 11,172자 전체가 동일한 18.38 px 고정폭**으로 들어 있습니다 — 한글 전용 블록이 통째로 탑재돼 있다는 뜻입니다.

> ⚠ 남은 확인: 이 라이브러리는 폰트 *메트릭*을 재현합니다. 자형(글자 모양)이 실제로 읽기 좋게 그려지는지는 **실기기에서 눈으로 확인**해야 합니다. 첫 시제품에서 가장 먼저 볼 항목입니다.

### 2-3. 카드원고 한 장이 한 화면에 들어가는가 — 결정적 실측

화면 576×288, padding 8, border 1 → **안쪽 558 px, 줄높이 27 px 고정 → 한 화면 최대 10줄**. 한글 연속 1줄에 **31자**, 공백 섞인 실제 문장은 **줄당 평균 37자**, 화면당 **약 370자**입니다.

목사님 카드원고의 실제 유형별로 측정했습니다.

| 카드 유형 | 글자수 | 차지하는 줄 | 판정 |
|---|---|---|---|
| 대지 선언 | 23자 | 1줄 / 10줄 | ✅ |
| 성구 카드(요 3:16) | 71자 | 3줄 / 10줄 | ✅ |
| 본문 인용(수 1:5-9) | 93자 | 4줄 / 10줄 | ✅ |
| 설명 카드(중간 길이) | 114자 | 4줄 / 10줄 | ✅ |
| **예화 카드(긴 편)** | **158자** | **4줄 / 10줄** | ✅ |
| 갈무리 권면 | 62자 | 2줄 / 10줄 | ✅ |

**전부 여유롭게 들어갑니다.** 가장 긴 예화 카드도 화면의 40%만 씁니다. 나머지 공간에 머리말(설교ID·본문·대지번호·경과시간)과 진행 표시를 넣을 여유가 충분합니다.

머리말 예시 `S1332 · 수 1:5-9 · ①  12:34 / 35:00` = 298 px (576 px 중) → **한 줄에 다 들어갑니다.**

**→ 설교앱의 `파일맵.cardArr` 를 손대지 않고 그대로 G2 페이지 배열로 쓸 수 있습니다.** 이것이 이 검토에서 가장 중요한 발견입니다.

## 3. 활용 방안 — 우선순위 순

### ★ 1순위 — 강단 프롬프터 (「토탈 설교 HUD」)

**해결하는 문제**: 강대상의 종이 원고나 아이패드를 내려다보는 시간. 고개를 숙이는 순간 회중과의 시선이 끊기고, 음성이 마이크에서 멀어지며, 손이 묶입니다.

**동작**
- 설교앱에서 설교를 고르면 그 설교의 카드 배열을 받아 캐시합니다.
- 한 화면 = 카드 한 장. **R1 반지 탭 = 다음 카드**, 더블탭 = 이전(루트에서는 종료).
- 상단 1줄에 `대지번호 · 본문 · 경과시간 / 목표시간` 상시 표시.
- 하단에 진행 막대(`━━━━━──────` 유니코드 블록 문자).
- 전환 바(이미지 전환 시점) 카드에는 `▶ 컷 07` 같은 표식 → 영상팀 신호와 동기가 맞습니다.

**왜 잘 맞는가**: 카드원고 스킬이 이미 "강단에서 슬쩍 봐도 한눈에 들어오게" 만들어 둔 물건입니다. G2의 제약(짧은 텍스트, 한 화면 한 덩어리)과 카드원고의 설계 의도가 **우연이 아니라 같은 방향**입니다.

**주의**: 설교자가 원고에 매이면 안 되므로, 화면은 **대지·핵심문장·성구만** 띄우고 설명 문장은 빼는 "요약 모드"를 기본으로 두는 편이 낫다고 봅니다. 전문 모드는 선택으로.

### ★ 2순위 — 설교 페이스 · 타이머

경과시간, 분당 속도, 목표 대비 편차를 화면 구석에 상시 표시합니다. 설교앱의 리허설 타이머가 이미 **공백 제외 분당 300자** 기준을 쓰고 있으므로 같은 기준을 그대로 옮기면 됩니다.

「지금 ②대지인데 예정보다 4분 빠름」 같은 한 줄이 강단에서 큰 도움이 됩니다. 1순위와 같은 앱 안에 넣습니다.

### ★ 3순위 — 음성 자동 추적 프롬프터

안경 마이크(16kHz PCM)를 열어 서버로 보내고, 전사 결과를 원고 텍스트와 정렬해 **카드를 자동으로 넘깁니다.** 손도 안 씁니다.

- 선례가 있습니다 — 꾸란 낭송을 실시간 인식해 해당 구절을 띄우는 앱(Taraweeh Companion), 말하는 속도를 피드백하는 프롬프터(PitchBeam)가 이미 G2에서 돌고 있습니다.
- **리스크**: 한국어 STT 지연, 강단 음향(회중 반응·반주), 즉흥 발언 시 정렬 실패.
- **반드시 수동 탭 폴백을 둡니다.** 자동 추적이 흔들려도 설교가 흔들리면 안 됩니다.
- 2단계 이후 과제로 두는 것이 안전합니다.

### 4순위 — 심방·상담 브리핑

성도를 만나기 직전, 이름·최근 기도제목·가정 상황·지난 심방 메모를 한 화면으로 봅니다. 손에 아무것도 들지 않고, 상대와 눈을 맞춘 채로.

⚠ **개인정보가 가장 민감한 용도입니다.** 서버 인증, 착용 해제 시 자동 잠금, 화면에는 최소 정보만, 저장은 하지 않기 — 이 네 가지를 설계에 먼저 박아야 합니다. 안경에는 카메라가 없어 촬영 우려는 없지만, 데이터는 별개 문제입니다.

### 5순위 — 성구 즉시 호출

이미 보유한 성경 데이터(`bible/bNN.json`)를 그대로 씁니다. R1 반지 스크롤로 절을 넘기며 낭독합니다. 새벽예배·기도회·심방 기도에서 성경책을 들지 않아도 됩니다.
→ 리스트 컨테이너는 펌웨어가 스크롤을 직접 처리해서 앱이 관여할 필요가 없습니다(항목 최대 20개, 항목당 64자).

### 6순위 — 예배 진행 큐시트

주보 순서(찬송 번호·교독문·기도 순서·광고)를 순서대로 넘깁니다. 사회를 볼 때 유용합니다. 설교앱에 이미 주보내용 공유 기능이 있으므로 데이터가 있습니다.

### 7순위 — 묵상 · 암송

이달의 묵상 본문, 암송 구절을 이동 중에 봅니다. G2용 성구 암송 앱(fill-in-the-blank 연습 포함)이 이미 공개돼 있어 참고할 구현이 있습니다.

### 8순위 — 예식서 프롬프터

결혼식·장례식·성찬식 예식문을 고개를 든 채로 낭독합니다. 가톨릭 성무일도를 스크롤 프롬프터로 읽는 앱이 이미 있습니다.

## 4. 설교앱과의 연결 설계 (권장안)

**G2 앱은 설교앱 안에 넣지 않고 별도 웹앱으로 만들되, 데이터는 공유합니다.**

이유: `index.html` 은 이미 단일 파일로 매우 큽니다. G2 앱은 UI 모델이 완전히 달라서(컨테이너 절대좌표) 코드를 섞으면 양쪽 다 나빠집니다.

### 데이터 전달 — 두 가지 안

**A안 (권장) — 설교앱이 "G2용 경량 JSON"을 따로 내보낸다**

설교앱에 **[👓 G2로 보내기]** 버튼을 하나 추가합니다. 누르면 그 설교의 카드 배열을 G2용 최소 형태로 줄여 시트(또는 파일맵)에 저장합니다.

```json
{
  "id": "S1332",
  "title": "강하고 담대하라",
  "ref": "수 1:5-9",
  "targetMin": 35,
  "cards": [
    { "t": "point", "n": "①", "s": "하나님은 함께 계심을 약속하십니다" },
    { "t": "verse", "r": "수 1:5", "s": "“내가 너를 떠나지 아니하며…”" },
    { "t": "body",  "s": "여러분, 이 말씀 앞에 서 보시기 바랍니다…" },
    { "t": "ill",   "s": "ex) 한 선교사가…" },
    { "t": "trans", "n": 7 }
  ]
}
```

장점: G2 앱이 원고 전문을 받지 않아 가볍고, 전달 형식이 설교앱 내부 구조 변경에 영향받지 않습니다. 오프라인에서도 안전합니다.

**B안 — G2 앱이 Apps Script를 직접 호출**

새로 만들 것이 없다는 장점이 있지만, 설교 행 전체(원고 전문 포함)를 WebView로 끌어와야 하고 CORS·응답 크기 부담이 있습니다. 시제품 단계에서만 쓰고 A안으로 옮기는 것을 권합니다.

### 저장 — 반드시 SDK 저장소를 쓸 것

⚠ **브라우저 `localStorage` 를 쓰면 안 됩니다.** `.ehpk` WebView 안에서는 앱이나 안경이 재시작하면 **지워집니다.** `bridge.setLocalStorage` / `getLocalStorage` 만 살아남습니다(삭제 API는 없어 빈 문자열로 지웁니다).

부팅 때 모든 키를 메모리 Map으로 한 번에 읽고, 읽기는 동기로 캐시에서, 쓰기는 백그라운드로 흘리는 패턴이 권장됩니다.

**마지막 위치(설교ID + 카드 인덱스)를 여기 저장**하면, 설교 중 연결이 끊겼다 붙어도 보던 카드로 돌아옵니다. 이건 선택이 아니라 필수 기능입니다.

## 6. 반드시 지킬 규칙 (심사·안정성)

1. **루트 화면 더블탭 = 종료 대화상자**(`shutDownPageContainer(1)`). Even Hub 제출 시 이걸 안 하면 반려됩니다.
2. `createStartUpPageContainer` 는 **정확히 한 번**만 호출. 자동 연결 경로가 둘이면 초기화가 두 번 돌아 이미지 전송이 겹칩니다(실제 보고된 버그).
3. **부팅 시 자동 연결.** 안경을 쓰고 있으면 폰을 꺼내 "연결" 버튼을 누를 수 없습니다.
4. `CLICK_EVENT = 0` 이 SDK에서 `undefined` 로 바뀝니다. `eventType === CLICK_EVENT || eventType === undefined` 로 함께 검사해야 합니다.
5. 스크롤 이벤트는 연타로 들어옵니다 — **300ms 쿨다운** 필수(설교 중 카드가 두 장씩 넘어가면 치명적입니다).
6. 시뮬레이터와 실기기의 이벤트 종류가 다릅니다(`sysEvent` vs `textEvent`/`listEvent`). **셋 다 처리**해야 합니다.
7. `containerName` 은 페이지당 고유, **최대 16자**.
8. `package_id` 는 하이픈 불가(`com.myname.sermonhud` 형태).

## 8. 아직 확인하지 못한 것 (정직하게)

1. **실기기 한글 자형** — 폰트에 글자가 있다는 것은 측정으로 확인했지만, 초록 단색 4비트로 렌더링된 한글이 강단 조명 아래서 얼마나 잘 읽히는지는 써 봐야 압니다. 받침이 많은 글자(뚫·꿇·삶)가 18.38px 폭 안에서 뭉개질 가능성이 있습니다.

3. **도수 렌즈** — 목사님 시력 교정이 필요하면 별도 확인이 필요합니다.
4. **공식 문서 원문** — 이 검토를 작성한 환경에서 `hub.evenrealities.com` 직접 접근이 네트워크 정책으로 차단돼, 공식 저장소(`even-realities/everything-evenhub`)와 커뮤니티 레퍼런스(`nickustinov/even-g2-notes`)를 1차 자료로 삼았습니다. 성능 수치는 커뮤니티 실측 1개 세션 기준이므로 절대값이 아니라 경향으로 보아야 합니다.
5. **Even Hub 심사 기준** — 개인 사이드로드로 쓸 계획이면 무관합니다.

## 10. 권고

**시작하실 것을 권합니다.** 다만 순서를 이렇게 잡으시길 제안드립니다.

1. **안경을 사기 전에** 0~1단계(시뮬레이터 시제품)를 먼저 해 보십시오. 클로드 코드 플러그인 설치부터 카드가 넘어가는 화면까지 반나절이면 닿습니다. 실제로 쓸 물건인지는 그 화면을 보면 판단이 섭니다.

가장 큰 이점은 기술이 아니라 **시선**입니다. 설교 중 고개를 숙이지 않아도 된다는 것 하나만으로도 만들 값어치가 있다고 봅니다.

## A-2. MemoMind One (XGIMI 인큐베이팅)

**구조가 G2와 놀랍도록 비슷합니다.** 공식 SDK 저장소(`memomind-open/plugin-open-platform`)를 직접 받아 확인했습니다.

```
[내 JS 플러그인]  ──gm 브리지──▶  [폰 컴패니언 WebView]  ──BLE──▶  [MemoMind One]
```

- `gm.display.createPage()` / `updateText()` / `closePage()` 로 HUD를 그립니다.
- `gm.audio.openCapture()` 가 실시간 Opus 스트림(모노 16 kHz, 20 ms 프레임)을 줍니다.
- 패키지는 `.mmpkg`, 빌드는 `./build.py` 한 줄.

### G2보다 나은 점 (설교 용도 기준)

1. **화면이 더 큽니다** — 600×350 = G2 대비 화소 약 1.27배. 줄 수와 한 줄 글자수 모두 늘어납니다.
2. **글자 크기를 2단계로 조절할 수 있습니다**(프로토콜 `0x08 font size`: 1=小, 2=大). **G2에는 이 API가 아예 없습니다.** 강단에서 "조금 더 크게"가 가능한지 여부는 실사용에서 꽤 큽니다.
3. **안경 위에서 직접 코드가 돕니다** — GlassSDK(C / RISC-V). G2 안경은 코드를 전혀 실행하지 않습니다. 폰 연결이 끊겨도 동작하는 프롬프터, 지연 없는 스크롤 같은 것이 원리적으로 가능합니다. 공식 예제에 **`novel_reader`(연속 세로 스크롤 리더)** 가 들어 있는데, 프롬프터와 사실상 같은 물건입니다.
4. **원시 프레임버퍼를 직접 그릴 수 있습니다**(GRAY_4 비트맵 + LZ4 타일). G2는 컨테이너 모델에 갇혀 있어 "가운데 정렬"조차 공백으로 흉내 내야 하지만, MemoMind는 픽셀을 직접 찍을 수 있으므로 **원하는 조판을 그대로 구현**할 수 있습니다.
5. **macOS Studio가 정식 제공**됩니다(유니버설 바이너리). 맥에서 바로 개발합니다.

### G2보다 나쁜 점

1. **한글을 확증할 수 없습니다.** 이것이 가장 큰 문제입니다.
   - SDK 문서 전체를 검색했으나 Korean / Hangul / CJK 언급이 **한 건도 없습니다.** 예제에 등장하는 언어는 영어와 중국어뿐입니다.
   - 폰트는 펌웨어가 소유하고(`fver`, `lang/font`는 "펌웨어 언어·폰트 설정"으로만 기술), **G2의 `@evenrealities/pretext` 같은 폰트 측정 도구가 없어** 제가 여기서 검증할 방법이 없습니다.
   - 간접 근거는 있습니다 — 실시간 번역 지원 언어에 **한국어가 포함**되고 퀵스타트 가이드가 한국어로도 인쇄됩니다. 번역 결과를 렌즈에 띄우는 기기이니 한글 글리프는 거의 확실히 있습니다. 다만 **"거의 확실"과 "측정했다"는 다릅니다.**
2. **클로드 코드 공식 플러그인이 없습니다.** G2는 `/glasses-ui`, `/font-measurement` 같은 스킬을 이븐 리얼리티가 직접 제공합니다. MemoMind는 문서를 읽고 제가 직접 구현해야 합니다 — 불가능하지 않지만 속도가 다릅니다.
3. **생태계가 갓 열렸습니다**(2026년 9월). G2는 프롬프터·성구 암송·기도 일지 같은 **베껴 쓸 선례가 이미 있습니다.**
4. 46.6 g 으로 G2보다 무겁습니다(RayNeo iO는 33 g).
5. 크로스벤더 오픈소스 SDK(MentraOS)가 **지원하지 않습니다** — 벤더 종속이 G2보다 큽니다.

## A-3. RayNeo iO (TCL)

**결론부터: 지금은 앱을 만들 수 없습니다.**

- RayNeo의 개발자 경로(Open Platform · ARDK)는 **X시리즈 전용**입니다 — 안경 자체가 안드로이드로 돌고, Unity/OpenXR APK를 ADB로 사이드로드하는 방식입니다. 소비자 펌웨어는 ADB를 숨은 제스처로 풀어야 하고, 자체 심사 없는 배포 창구가 없습니다.
- **iO는 그 계열이 아닙니다.** 33 g · 240 mAh · 0.085cc Firefly Nano 엔진의 경량 컴패니언 기기로, 안드로이드를 얹을 여지가 없습니다. **iO용 폰 컴패니언 SDK는 공개된 것이 없습니다.**
- MentraOS 같은 크로스벤더 SDK도 RayNeo를 지원하지 않습니다.

다만 **완제품 기능으로는 매력적**입니다 — **자동 텔레프롬프터가 내장**돼 있고, 55개 언어 실시간 자막·번역(약 1초 지연), 1,300 nit 밝기, 이틀 가는 배터리, 33 g.

→ 그러나 목사님 용도에는 결정적 한계가 있습니다. **설교앱의 카드원고와 연동되지 않습니다.** 내장 프롬프터는 "긴 텍스트를 흘려보내는" 물건이지, 목사님이 쓰시는 **카드 단위 제어·대지 번호·전환 컷 표시·경과시간**을 할 수 없습니다. 원고를 매번 손으로 옮겨 붙여야 하고, 예화 하나를 고치면 다시 옮겨야 합니다.

**요약**: RayNeo iO는 "앱을 만들 기기"가 아니라 "완제품을 그대로 쓸 기기"입니다. 토탈 설교 앱을 중심에 두시는 이상 후보에서 빠집니다.

## A-4. 권고

**Even Realities G2를 1순위로 유지하시길 권합니다.** 근거 세 가지입니다.

1. **한글을 실제로 측정해 확인한 유일한 기기**입니다. 나머지 둘은 추정입니다.
2. **이븐 리얼리티가 클로드 코드 공식 플러그인을 직접 제공**합니다. 목사님이 클로드 코드로 개발하시겠다는 계획과 정확히 맞물립니다 — 이건 다른 두 기기에 없는 이점입니다.
3. **선례가 많습니다.** 프롬프터·낭송 인식·성구 암송·기도 일지가 이미 G2에서 돌고 있어, 처음부터 발명할 것이 적습니다.

**MemoMind One은 진짜 대안이며, 한 가지 조건에서 역전됩니다.**
G2 실기기에서 **한글 자형이 작아 강단에서 읽히지 않을 경우**입니다. MemoMind는 화면이 27% 넓고 **글자 크기를 키울 수 있으며** 픽셀을 직접 그릴 수 있어, 그 문제에 대한 답을 갖고 있습니다.

→ 그래서 앞 §7 로드맵의 **2단계(실기기 한글 가독성 확인)가 더욱 중요한 분기점**이 되었습니다. 여기서 통과하면 G2로 직진, 막히면 MemoMind One으로 선회하는 구도입니다. 두 기기 모두 **폰 WebView 웹앱 + 텍스트 HUD** 라는 같은 골격이라, 설교앱 연동부(§4의 경량 JSON)와 카드 분할 로직은 **그대로 재사용**됩니다. 갈아타는 비용은 화면 그리는 층 하나뿐입니다.

**RayNeo iO는 제외**합니다. 다만 "앱 없이 당장 프롬프터만 써 보고 싶다"면 시험해 볼 가치는 있습니다.
